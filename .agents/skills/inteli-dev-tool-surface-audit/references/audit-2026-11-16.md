# Аудит поверхности инструментов — 2026-11-16

Повод: в CRM появился домен **брифов** (перенос функционала `inteli-dev-brif-telegram-bot`). Проверялось, что новая доменная операция получила владельца в MCP и у Кики, а старые поверхности не разъехались.

## Что изменилось в домене

| Возможность | Где живёт | MCP | Кики |
|---|---|---|---|
| Список брифов с фильтрами | `GET /admin/briefs`, `GET /briefs` | `list_briefs` | `list_briefs` |
| Карточка брифа с ответами по секциям | `admin.briefs.show` | `get_brief` | `get_brief` |
| Создать бриф из шаблона | `admin.briefs.create/store` | `create_brief` | — |
| Вернуть на доработку | `admin.briefs.reopen` | `reopen_brief` | — |
| Архив | `admin.briefs.archive` | `archive_brief` (confirm) | — |
| Каталог шаблонов | `briefs:seed` | `list_brief_templates` | — |
| Заполнение и отправка клиентом | `client.briefs.save/submit` | — | — |
| Экспорт PDF/JSON/Markdown | `admin.briefs.export` | — | — |

Решения:

- **Заполнение и отправка — только UI.** Бриф заполняет клиент под своей подписью; агент не должен отправлять его за него.
- **Экспорт — только UI.** Это файлы (PDF/MD/JSON) для пересылки клиенту, а не доменное чтение; агенту хватает `get_brief`.
- **Создание/архив — MCP, но не Кики.** Это owner-level действия; в чате они создают клиентские артефакты без явного запроса. Кики видит брифы на чтение.
- **Архив требует `confirm: true`** — как удаление отчёта.

## Остаточные gaps

- REST API v1 (`/api/v1`) брифы не отдаёт — публичный API пока про задачи/счета/проекты. Решение: отдельная задача, если появится внешний потребитель.
- У МСР нет инструмента экспорта брифа; при необходимости добавлять как `get_brief` с форматом, а не как файловый стрим.
- `Site MCP` не затрагивался: брифы принадлежат CRM.

## Дополнение: шаблоны брифов через Кики

Появилась авторская работа со схемой брифа. Решение: схему создаёт и правит только Кики, админка умеет лишь удалять.

| Возможность | MCP | Кики | Админка |
|---|---|---|---|
| Каталог шаблонов | `list_brief_templates` | `list_brief_templates` (в контексте) | `/admin/briefs/templates` |
| Создать шаблон | — | `create_brief_template` | — |
| Выдать бриф клиенту | `create_brief` | `create_brief` (confirm, task_id → клиент/проект) | кнопка «Создать бриф» |
| Изменить схему | — | `update_brief_template` (confirm) | — |
| Удалить шаблон | — | `delete_brief_template` (confirm) | кнопка «Удалить» |

Почему так: второй редактор схемы в админке разошёлся бы с `BriefSchema`, а `validateDefinition()` уже
ловит неизвестные типы, пустые секции и `options` без вариантов. Удаление — единственное действие,
которому не нужна схема, поэтому оно продублировано в UI для быстрых операций.
