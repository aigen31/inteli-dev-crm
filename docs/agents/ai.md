# Kiki assistant (CRM adapter)

> Модель, история, сессии и tool loop живут в
> `inteli-dev-kiki-assistant-kernel-api`. CRM остаётся владельцем клиентов,
> задач, счетов, файлов, прав и подтверждений. Ниже — актуальный поток.

## Два входа, одно ядро

- `/assistant` — полноценное рабочее место: список сессий, поиск, пины,
  архив, переименование, изображения и формы заявок.
- `Components/Assistant/AssistantPanel.vue` — плавающая панель (`⌘K`,
  кнопка в сайдбаре, мобильная кнопка). Панель показывает последний диалог и
  умеет всё то же, кроме списка сессий; кнопка «открыть на весь экран»
  переводит в `/assistant?c={id}`.

Оба входа используют `useAssistantChat` и один набор компонентов
(`ChatThread`, `MessageBubble`, `Composer`), поэтому поведение не расходится.

## Поток сообщения

`Composer` → `POST /assistant/chat` → `AgentService::chat` → `KernelClient` →
`POST /v1/chat` ядра. Ядро вызывает CRM обратно:

- `GET /api/internal/assistant/profile` — правила роли и JSON-схемы
  инструментов;
- `POST /api/internal/assistant/tools/{tool}` — выполнение инструмента;
- `GET /api/internal/assistant/files/{file}` — байты изображения для модели.

CRM проверяет `KERNEL_PROVIDER_TOKEN` и `X-Kernel-Channel: crm`, загружает
пользователя по `actor.id`, применяет роли в `CrmToolbox`.

## Сессии

Ядро — источник истины: заголовок, пин, архив, список, удаление. CRM держит
`ai_conversations` как зеркало, потому что на него ссылается `ai_actions` и
потому что список должен открываться, даже если ядро на минуту недоступно.

- `SessionService::list()` сначала спрашивает ядро; при `AiException`
  отдаёт локальное зеркало (`source: local`).
- Переименование, пин и архив идут в ядро, затем в зеркало. Если ядро
  ответило ошибкой, UI показывает её и не врёт про сохранение.
- `POST /assistant/conversations` выдаёт UUID новой сессии, но строку не
  создаёт: пустые «новые диалоги» не засоряют список. Строка появляется с
  первым сообщением.
- `regenerate` удаляет хвост ответа и в CRM, и в ядре, поэтому дубликата
  вопроса в истории не остаётся.

Эндпоинты:

| Метод | Маршрут | Что делает |
|---|---|---|
| GET | `/assistant/conversations?q=&archived=` | список сессий |
| POST | `/assistant/conversations` | выдать id новой сессии |
| GET | `/assistant/conversations/{id}` | сообщения и pending actions |
| PATCH | `/assistant/conversations/{id}` | `title`, `pinned`, `archived` |
| DELETE | `/assistant/conversations/{id}` | удалить у ядра и локально |
| POST | `/assistant/conversations/{id}/regenerate` | ответить заново |

## Изображения

1. `POST /files/upload` кладёт файл в `storage/app/attachments` и возвращает
   UUID (`FileAttachment`).
2. `POST /assistant/chat` получает `attachments: [uuid]`; `AgentService`
   проверяет владельца и MIME `image/*`, максимум 4 штуки.
3. CRM отправляет в ядро только `{id, name, mime}`.
4. Ядро забирает байты через `/api/internal/assistant/files/{file}` с
   сервисным токеном. Эндпоинт отдаёт файл, только если он принадлежит
   актору **и** приложен к сообщению этого диалога.
5. В модель изображение уходит `data:`-URL в текущем ходе. В следующих ходах
   история содержит текстовую пометку, а не повторную картинку.

Если маршрут модели текстовый (`KERNEL_CLOUD_VISION=false` или
`KERNEL_LOCAL_VISION=false`), ядро отвечает `422`, а CRM показывает:
«Эта модель не умеет читать изображения…». Молча терять картинку нельзя.

## Задачи из форм заявок

Модель не создаёт задачу «на глаз»: она собирает структурированную заявку.

1. `list_form_templates` — ключи, названия и схема полей (типы, обязательные,
   варианты, repeat-группы).
2. `create_task_from_form` — инструмент с `confirm: true`. Ядро получает
   `pending_action`, CRM создаёт `ai_actions(status=proposed)`.
3. `CrmToolbox::formPayload()` отдаёт в UI шаблон, схему и предзаполненные
   значения. Проверка шаблона происходит **до** показа формы: битый template
   id возвращается модели как ошибка инструмента.
4. UI рисует `FormActionCard` (StructuredForm + название, приоритет, срок,
   клиент для админа). Пользователь правит поля и подтверждает.
5. `POST /assistant/actions/{id}/confirm` с `arguments` перезаписывает
   аргументы действия и выполняет `FormTemplateService::createTask()`.
6. Ошибка валидации (`422`) не убивает действие: оно остаётся `proposed`,
   поля подсвечиваются, пользователь исправляет и подтверждает снова.
7. После успеха в историю добавляется заметка со ссылкой на задачу.

Админ обязан выбрать клиента: `client_id` обязателен, список клиентов
приходит в payload формы. Клиент создаёт заявку только себе.

## Подтверждения

Инструмент с `confirm=true` создаёт `ai_actions(status=proposed)` и
возвращает `pending_action`. Ядро останавливает tool loop. Для форм —
`type: form` и блок `form`; для остальных — `type: action` и `summary`.

Права перепроверяются при confirm: `CrmToolbox::execute()` заново проверяет
роль и доменные правила. Действие живёт 30 минут.

## Данные

- модель, диалоги, сессии, изображения (ссылки): ядро;
- клиенты, задачи, счета, файлы, `ai_actions`: PostgreSQL CRM;
- внутренние и секретные данные CRM по умолчанию идут только в локальную
  модель (`KERNEL_DATA_CLASS=internal`, `KERNEL_ALLOW_CLOUD_FOR_INTERNAL=false`).

## Что взято из OpenWebUI и соседних ассистентов

Реализовано:

- список сессий с поиском, пинами, архивом и группировкой по дате;
- переименование и удаление сессии;
- вложения-изображения: кнопка, вставка из буфера, drag&drop, превью,
  удаление до отправки;
- «Ещё раз» для последнего ответа и копирование ответа;
- pending actions как карточки в ленте, а не модалка поверх чата;
- пустой экран с подсказками и персонажем;
- прозрачность маршрута: бейдж «локальная модель / облако» в шапке.

Отложено осознанно:

- потоковая выдача токенов: tool loop и подтверждения ломают простой SSE,
  нужен отдельный контракт событий (`meta` / `delta` / `tool` / `done`);
- папки и теги сессий: пин + поиск закрывают текущий объём;
- ветвление от сообщения: требует хранения дерева, а не линейной истории;
- RAG по документам: у CRM нет корпуса знаний, кроме форм и шаблонов.

## Ограничения

- Зеркало сессий может отставать от ядра; источник истины — ядро.
- Rate limit 30/мин на маршрутах ассистента (чат, список, confirm).
- Заголовок сессии обрезается до 80 символов.
- `lang/` в проекте не опубликован, поэтому `FormTemplateService` задаёт
  явные сообщения для групп, а `useAssistantChat` переводит частые
  `validation.*` ключи. Новые правила валидации форм стоит сопровождать
  сообщением.

## Документы → план задач

1. `POST /assistant/documents` (multipart) извлекает текст и создаёт
   `ai_documents`. Поддержаны `xlsx`, `docx`, `pptx`, `pdf`, `csv`, `txt`,
   `md`, `json`, `xml`, `html`, `yaml`, `rtf`; лимит 20 МБ, 200 тыс. символов.
2. В ядро уходит **манифест**: id, имя, MIME, число символов, первые 240
   символов. Полный текст в промпт не попадает.
3. Модель читает через `read_document`:
   - `offset`/`limit` — последовательные куски до 12 тыс. символов;
   - `query` — поиск по строкам с контекстом (до 40 совпадений).
4. Модель выбирает подход: готовая форма → `create_task_from_form`; шаблон →
   `template_id` в плане; иначе `propose_task_plan`.
5. `propose_task_plan` создаёт `pending_action(type=plan)`; UI рисует
   редактируемую карточку (`TaskPlanCard`). Подтверждение создаёт **все**
   задачи одной операцией, `source=ai`, с чек-листами и сроками.

Почему план, а не N вызовов `create_task`: пользователь видит весь список до
создания и может убрать лишнее; частичный сбой не оставляет половину задач.

## Проекты

Проект — контейнер работы (ADR-0009). У него есть ключ (`KOR`), название,
клиент, статус, приоритет, цвет, сайт, `AGENTS.md`, указания и даты.

- Задачи привязаны к проекту (`tasks.project_id`) и получают номер внутри
  проекта: `KOR-1`, `KOR-2`. Ссылка читаемая и уникальна.
- Прогресс — по группам состояний: очередь / в работе / готово / отменено.
- `/admin/projects` — портфель, `/admin/projects/{id}` — обзор, задачи и
  контекст, `/admin/projects/{id}/edit` — настройки.
- Задача создаётся с проектом: селектор в форме, `?project_id=` в ссылке,
  фильтр на `/admin/tasks`.

### Контекст и изучение сайта

Сайт, `AGENTS.md` и указания принадлежат проекту, а не общим настройкам.
`ProjectContext::promptFor($project)` собирает блок для системного промпта;
если диалог не привязан к проекту, остаётся fallback на старые настройки.

Профиль провайдера получает `conversation_id`; CRM находит диалог, его проект
и подмешивает именно этот `AGENTS.md` (лимит 7 тыс. символов, заголовки
сохраняются).

Изучение сайта — история проекта:

- `project_studies` хранит автора, kernel study id, события, результат, ошибку;
- «Изучить сайт» на странице проекта запускает study и показывает живой поток;
- по завершении `AGENTS.md` сохраняется в проект, редактор остаётся для правок;
- история последних изучений видна в карточке проекта.

Эндпоинты: `POST /admin/projects/{project}/study`,
`GET /admin/projects/{project}/study/{study}`,
`POST /admin/projects/{project}/study/{study}/cancel`.

## Прайс-лист из ядра

Прайс принадлежит сайту, но ядро отдаёт его всем каналам:

- `GET /v1/knowledge/pricing` — снимок с TTL (`KERNEL_PRICING_TTL_SECONDS`);
- встроенный инструмент `get_price_list` доступен любой модели в tool loop;
- при недоступности сайта отдаётся последний снимок с `stale: true`.

CRM не хранит копию прайса: модель вызывает инструмент, когда цена важна.

## Ход работы

Ядро возвращает `trace` (заметки модели, инструменты, статус, длительность,
краткий результат). CRM сохраняет его в `ai_messages.trace` и показывает
раскрывающийся блок «Ход работы» под ответом. Для study — отдельный поток
событий в настройках проекта.

## Ограничения новых сценариев

- `KERNEL_MAX_OUTPUT_TOKENS` (по умолчанию 8000): план на 20–30 задач
  помещается; при обрезке ядро отвечает `422` с просьбой сократить объём.
- Модель переносит в план **все смысловые работы** документа; подпункты
  группируются, но работы не теряются.
- `read_document` без `document_id` берёт последний документ пользователя;
  при нескольких документах модель обязана передать id из манифеста.


## Доступ к проектам и задачам

- Владелец проекта — `projects.client_id`; администраторы видят все проекты.
- `project_members` даёт явный доступ с ролью `manager` / `member` / `viewer`.
  Наблюдатель не может создавать задачи; владелец и участники могут, менеджер
  дополнительно видит состав команды.
- `ProjectPolicy` закрывает просмотр/редактирование/участников; клиенты не
  редактируют настройки проекта.
- `Task::visibleTo($user)` требует и `task.client_id = user`, и доступ к
  проекту: отзыв участия скрывает задачи, не удаляя их.
- Клиентский портал: `/projects`, `/projects/{project}` — только доступные
  проекты и только свои задачи; AGENTS.md и участники клиенту не отдаются.
- Ассистент: `list_projects`, `resolveProject`, план и поиск задач используют
  те же scope; наблюдателю план в проекте недоступен. Профиль проверяет
  видимость проекта, поэтому после отзыва `AGENTS.md` не попадает в промпт.

Управление доступом — в карточке проекта, блок «Доступ к проекту»
(`POST/PATCH/DELETE /admin/projects/{project}/members`).

## Отчёты о выполнении

- У отчёта есть необязательный **заголовок** (`task_reports.title`); без него
  используется «Отчёт от {дата}».
- Формат — повторяемые группы: **краткое объяснение → ссылка страницы для
  тестирования (опционально) → скриншот (опционально)**. Групп может быть
  сколько угодно (`task_report_items`), старые отчёты мигрированы в одну.
- Отчёт можно создать отдельно от задачи (`task_id` nullable) и отправить
  конкретному пользователю (`recipient_id`). Получатель видит его в
  `/reports`, автор/админ — в `/admin/reports`; первое открытие ставит
  `read_at`, уведомление уходит на почту и в базу.
- Отдельная страница отчёта — `/reports/{report}`: заголовок, все группы, получатель, задача и статус прочтения. Карточка в списке показывает только заголовок, превью и метаданные — детали задачи только на странице.
- Скриншот отдаётся через `/reports/{report}/screenshot?item={item}` с
  проверкой доступа к отчёту; общий файловый маршрут для чужих скриншотов не
  используется.
- MCP: `POST /api/mcp` (Bearer `MCP_TOKEN`), инструмент
  `create_task_report` принимает `items[]`; `list_users`, `list_tasks`,
  `list_reports` помогают агенту выбрать получателя и задачу. DeepSeek
  Harness видит их как `mcp__crm__*`.
