# ADR-0008: Document-to-plan tasks, project memory and shared prices

## Статус

Accepted, 2026-11-05. Дополняет ADR-0007 и контракт ядра
(`inteli-dev-kiki-assistant-kernel-api/docs/ADR-003`).

## Контекст

Документы (брифы, таблицы, ТЗ) приходили в чат как обычный текст или не
приходили вовсе. Задачу из документа приходилось создавать вручную, по одной,
а ассистент не знал ни сайта проекта, ни его правил. Прайс-лист жил только на
сайте и был недоступен другим ассистентам.

Нужно было: разобрать любой текстовый документ, предложить **план задач**,
дать ассистенту память о проекте (AGENTS.md) и один источник цен.

## Решение

### Документ — ссылка, а не промпт

CRM извлекает текст один раз при загрузке (`DocumentExtractor`: xlsx, docx,
pptx, pdf, csv, txt/md/json/html) и хранит его в `ai_documents`. В ядро уходит
только манифест: `id`, имя, MIME, число символов, первые 240 символов.

Модель читает текст через инструмент `read_document`:
- `offset`/`limit` для последовательного чтения;
- `query` для поиска по строкам с контекстом.

Почему не передавать текст целиком: документ на 200 тыс. символов занимает
почти весь контекст, повторяется в каждом следующем запросе и вытесняет
историю. Манифест + управляемое чтение дают модели ровно столько, сколько
нужно для текущего шага.

### План задач — отдельный тип подтверждения

`propose_task_plan` возвращает не одну задачу, а список. Ядро создаёт
`pending_action` с `type: plan`; UI рисует редактируемую карточку: название,
приоритет, чек-лист, описание, срок. Подтверждение создаёт все задачи одной
операцией.

Альтернатива «модель вызывает `create_task` N раз» отвергнута: пользователь
не видит план целиком, задачи создаются до проверки, а частичный сбой
оставляет половину списка.

### Проект — настройка, а не задача

> Уточнение ADR-0009: контекст проекта (сайт, `AGENTS.md`, указания) переехал
> из общих настроек в сущность проекта; глобальные ключи остались fallback.

Сайт, `AGENTS.md` и постоянные указания хранятся в `settings` и попадают в
системный промпт каждого хода (с ограничением размера и сохранением
заголовков). Изучение сайта запускается из настроек и идёт асинхронно через
DeepSeek Harness; прогресс виден в UI.

`AGENTS.md` пишет отдельный агент по скиллам `create-agentsmd` и
`writing-for-agents`: он читает `sitemap.xml` и максимум 5 страниц, сжимает
HTML до текста и оставляет только проверенные факты. Это дешевле, чем каждый
раз объяснять контекст в чате.

### Цены — проекция ядра

Прайс принадлежит сайту. Сайт отдаёт снимок по внутреннему контракту
(`/internal/assistant/prices`, сервисный токен), ядро кэширует его в SQLite
(`KERNEL_PRICING_TTL_SECONDS`) и отдаёт всем каналам:
`GET /v1/knowledge/pricing` и встроенный инструмент `get_price_list`.

Кэш переживает недоступность сайта: при ошибке отдаётся последний снимок с
флагом `stale`, а не «цен нет». Так ассистент не выдумывает стоимость и не
ломается от минутного сбоя.

### Процесс виден

Ядро возвращает `trace`: заметки модели, вызовы инструментов, статус,
длительность и краткий результат. CRM хранит его на сообщении и показывает
раскрывающийся «Ход работы». Длинное изучение сайта показывает живой поток
событий, а не спиннер.

## Последствия

Положительные:

- документ не раздувает контекст и не дублируется в истории;
- план можно проверить и отредактировать до создания задач;
- AGENTS.md переиспользуется всеми будущими задачами;
- цены согласованы между сайтом, CRM и будущими каналами;
- пользователь видит, что агент делает, и не считает интерфейс зависшим.

Отрицательные:

- извлечение документа — ещё один шаг, который может не поддержать формат;
- `read_document` добавляет round trip к CRM;
- AGENTS.md может устареть; его нужно обновлять изучением или вручную;
- кэш цен может отставать на TTL.

Меры:

- неподдержанный формат возвращает понятную ошибку, а не пустой документ;
- чтение ограничено 12 тыс. символов за вызов и 200 тыс. на документ;
- в настройках видно дату изучения и содержимое AGENTS.md;
- stale-снимок помечается, а TTL настраивается.
