# ADR-0010: Project and task access control

## Статус

Accepted, 2026-11-05. Дополняет ADR-0009.

## Контекст

Проект был виден всем администраторам и своему клиенту; задачи клиента —
только ему. Не было способа дать доступ второму участнику, ограничить его
ролью или отозвать доступ, не удаляя задачи. Клиентский портал не показывал
проекты вовсе.

## Решение

### Владелец и участники

Владелец проекта — `projects.client_id` (клиент, для которого ведётся работа).
Администраторы видят все проекты: это студия, а не арендатор.

`project_members` добавляет явный доступ:

- `manager` — видит проект, задачи и состав команды, может создавать задачи;
- `member` — видит проект и задачи, может создавать задачи;
- `viewer` — только просмотр проекта и **своих** задач.

Владелец имеет доступ всегда; отозвать его нельзя, можно сменить владельца
проекта.

### Политики

`ProjectPolicy`:

- `view` — админ, владелец или участник;
- `update`/`archive`/`manageMembers` — только админ;
- `createTask` — владелец, менеджер, участник; наблюдателю нельзя.

`TaskPolicy::view` для клиента требует одновременно `task.client_id = user` и
доступ к проекту. Поэтому отзыв участия скрывает задачи проекта, не удаляя их.
`Task::visibleTo($user)` — единый scope для списков, портала и ассистента.

### Клиентский портал

`/projects` и `/projects/{project}` показывают только доступные проекты и
только задачи этого клиента. Внутренние материалы (AGENTS.md, изучение сайта,
участники) клиенту не отдаются. Прогресс считается по его задачам.

### Ассистент

`list_projects`, `resolveProject` и план задач используют `Project::visibleTo`.
Наблюдатель не может предложить план в проекте; попытка возвращает понятную
ошибку. Задачи клиента ищутся через `Task::visibleTo`, поэтому отозванный
проект исчезает и из ответов Кики. Профиль ассистента проверяет видимость
проекта диалога: после отзыва доступа `AGENTS.md` больше не попадает в промпт.

## Последствия

Положительные:

- доступ выдаётся и отзывается без удаления данных;
- роли ограничивают создание задач;
- клиент видит свои проекты и только свои задачи;
- один scope используется в UI, политиках и ассистенте.

Отрицательные:

- администратор по-прежнему видит всё (осознанно);
- роль применяется к клиентам, а не к отдельной команде;
- при отзыве доступа задачи остаются в базе.

Меры: политики + scope, тесты на владельца/участника/наблюдателя/постороннего,
история действий через `added_by`.
