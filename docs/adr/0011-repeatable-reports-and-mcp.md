# ADR-0011: Repeatable report groups and the CRM MCP server

## Статус

Accepted, 2026-11-05.

## Контекст

Отчёт о задаче был одним текстовым блоком. Нужен формат «краткое объяснение —
ссылка страницы для тестирования — скриншот», причём таких групп в одном
отчёте может быть сколько угодно (одна на проверяемую вещь). Отчёт должен
создаваться отдельно от задачи, доставляться конкретному пользователю и быть
доступным агенту через MCP.

## Решение

### Отчёт = шапка + повторяемые items

`task_reports` хранит заголовок, получателя, автора, опциональную задачу и
дату отправки.
Тело — `task_report_items` с `position`, `content`, `test_url`,
`screenshot_id`. Старые отчёты мигрированы в одну группу, поэтому история
читается тем же компонентом.

Группы не ограничены валидацией; практический предел — размер HTTP-запроса и
лимит скриншота 10 МБ.

### Доставка

Получатель обязателен. Отчёт виден автору, получателю и администратору;
клиент видит только адресованные ему отчёты (и легаси-отчёты по своим
задачам). Создание фиксирует `sent_at`, уведомление уходит в базу и на почту;
первое открытие получателем ставит `read_at`. Скриншот отдаётся через
`/reports/{report}/screenshot?item=...` после проверки доступа к отчёту, а не
через общий файловый маршрут.

### MCP

CRM поднимает `/api/mcp` (JSON-RPC 2.0, токен `MCP_TOKEN`) с инструментами
`create_task_report`, `list_users`, `list_tasks`, `list_reports`. Создание
идёт через тот же `ReportService`, что и веб-форма, поэтому формат и права не
дублируются.

DeepSeek Harness подключается как `dsh-mcp-client` (streamable HTTP) через
insert-патч `/data/mcp.yml`, который sidecar генерирует из `CRM_MCP_URL` и
`CRM_MCP_TOKEN` на старте. Агент видит `mcp__crm__create_task_report`.

## Последствия

Положительные:

- одна группа = одна проверяемая вещь; отчёт масштабируется без новых полей;
- отчёт отделяется от задачи, но может быть к ней привязан;
- один сервис для веба и агентов;
- отчёт открывается отдельной страницей `/reports/{id}`: заголовок, все группы, получатель, задача и статус прочтения;
- в списке карточка показывает только заголовок, превью и метаданные — без деталей задачи;
- доставка и прочтение отслеживаются.

Отрицательные:

- у отчёта две таблицы вместо одной;
- скриншоты занимают место в локальном хранилище;
- MCP-токен — общий секрет, его нужно ротировать.

Меры: каскадное удаление items, лимит 10 МБ на скриншот, проверка получателя
и политики на каждом маршруте, токен только в env.
