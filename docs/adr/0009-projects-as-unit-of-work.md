# ADR-0009: Projects as the unit of work

## Статус

Accepted, 2026-11-05. Дополняет ADR-0007 и ADR-0008.

## Контекст

Задачи были плоским списком: клиент, статус, дедлайн. Контекст проекта
(сайт, AGENTS.md, указания) жил в общих настройках, поэтому два проекта одного
клиента делили одну инструкцию. Не было прогресса, ключей задач и истории
изучения.

В зрелых PMS проект — это контейнер работы: у него есть ключ и нумерация
задач, состояние, ответственный/клиент, сроки, прогресс по состояниям,
участники, метки, milestones и активность (Plane, Linear, Asana, ClickUp).
Мы взяли минимальный, но честный набор.

## Решение

### Проект — сущность, задача — его часть

`projects`: ключ (`KOR`), название, описание, клиент, статус, приоритет, цвет,
сайт, `AGENTS.md`, указания, даты, архив. `tasks.project_id` — nullable, чтобы
старые задачи не ломались; новые задачи получают `project_id` и номер.

Номер задачи — `max(number)+1` внутри проекта, отображается как `KOR-12`.
Это даёт читаемые ссылки и не требует глобального счётчика. Уникальность
держит индекс `(project_id, number)`.

### Контекст проекта вместо глобальных настроек

Сайт, `AGENTS.md` и указания переехали в проект. `ProjectContext` собирает
блок для конкретного проекта; для диалогов без проекта остаётся fallback на
старые настройки. Профиль провайдера получает `conversation_id`, поэтому ядро
подмешивает AGENTS.md именно того проекта, в котором идёт диалог.

### Изучение сайта — история проекта

`project_studies` хранит локальную запись: кто запустил, kernel study id,
события, результат, ошибку. Это даёт историю и переживает перезагрузку
страницы. По завершении `AGENTS.md` автоматически сохраняется в проект, а
редактор остаётся для ручной правки.

### Прогресс по группам состояний

Прогресс считается по группам: очередь (pending/queued), в работе
(in_progress/awaiting_review), готово (completed), отменено. Проценты — доля
готовых. Это устойчивее, чем «средний статус», и совпадает с тем, как Plane
показывает распределение work items по state groups.

### Задачи из документа создаются в проекте

`propose_task_plan` принимает `project_id`; если его нет, берётся проект
диалога. План можно проверить, убрать лишнее и создать все задачи одной
операцией. Для брифа на 26 строк план на 30 задач помещается в один ответ
(`KERNEL_MAX_OUTPUT_TOKENS=8000`).

## Последствия

Положительные:

- у задач есть читаемые ссылки и принадлежность;
- контекст и изучение не смешиваются между проектами;
- прогресс и сроки видны на одном экране;
- один запрос создаёт весь пул задач из документа.

Отрицательные:

- номер задачи назначается без распределённой блокировки (при параллельном
  создании возможен конфликт; для одного администратора допустимо);
- архив не удаляет задачи;
- старые задачи остаются без проекта, пока их не разложат.

Меры: уникальный индекс, транзакция на создание плана, nullable project_id,
архив вместо удаления.
