# ADR-0002: Типизированные пользовательские поля

## Статус

Accepted, 2026-10-31.

## Контекст

Нужны поля разного назначения (статус приёма заявок, канал связи, критерии приёмки), доступные в карточке, фильтрах, REST и MCP. Проект уже использовал PostgreSQL и Eloquent; хранение всех значений в одном JSON упрощает схему, но ломает фильтрацию, валидацию и читаемость API. EAV с отдельной таблицей на тип — гибко, но много JOIN и сложная миграция.

## Решение

Гибрид:

- `custom_fields` — метаданные (entity, key, type, options, default, required, flags);
- `custom_field_values` — одна строка на (field, entity) с типизированными колонками `value_text`, `value_number`, `value_date`, `value_boolean`, `value_json`;
- `CustomFieldService` — единственная точка валидации, записи, дефолтов, сериализации и фильтров;
- значения отдаются объектом `key → {field_id,label,type,value,display}`; дефолты включаются, даже если строки ещё нет.

`intake_status` — обычное select-поле с дефолтом `open`, а не отдельная сущность: для соло-практики статус приёма — атрибут клиента, а не workflow.

## Альтернативы

- **Один JSON-блоб**: проще схема, но нет индексов/фильтров и типовой валидации.
- **Полный EAV**: гибко, но дорогие выборки и сложный код.
- **Физические колонки на каждое поле**: быстрые фильтры, но миграция на каждое поле и жёсткая схема.
- **Отдельная `intake_stages`**: уместно при нескольких переходах и SLA; сейчас overkill.

## Последствия

- Фильтры и API работают по типизированным колонкам; `value_json` — только для multiselect.
- Добавление поля — запись в `custom_fields`, без миграции.
- Нужно следить за `key` (уникален в рамках entity) и `options` для select.
- Для горячих полей при росте можно добавить проекционные колонки/индексы.
